# hagitask-community-packages

Source of truth for the public HagiTask community catalog.

This repository is mounted by [`hagitask-site`](https://github.com/HagiCode-org/hagitask-site)
as its `community-packages/` Git submodule. The site build reads task packages from
`community-packages/data/`, validates them against the authoritative schemas, generates
`/index.json`, `/tasks/<taskId>.json`, and downloadable `/packages/<taskId>.zip` archives,
then publishes them as static assets.

## Source Data vs Generated Output

Every `data/<taskId>/` directory in this repository is **source data**. Everything the public
site serves is **generated** and must never be edited or committed by hand.

| Artifact | Where it lives | Who owns it |
| --- | --- | --- |
| `data/<taskId>/` package directories | this repository | contributors (edit here) |
| `community-packages/` submodule | `hagitask-site` | pins a commit of this repository |
| `/index.json` | `tasks.hagicode.com` | generated by the site build |
| `/tasks/<taskId>.json` | `tasks.hagicode.com` | generated by the site build |
| `/packages/<taskId>.zip` | `tasks.hagicode.com` | generated by the site build |
| `hagitask/` nested submodule | this repository (pins [`hagitask`](https://github.com/HagiCode-org/hagitask)) | schema maintainers |

```text
hagitask-community-packages/data/<taskId>/   (you edit this)
        │
        │ git submodule → hagitask-site/community-packages/
        ▼
hagitask-site build                          (normalize → validate → publish)
        │
        ├─ /index.json                        discovery index
        ├─ /tasks/<taskId>.json              detail document
        └─ /packages/<taskId>.zip            installable archive
```

The archive is a byte-stable zip of the whole `data/<taskId>/` directory, so any file you add
to the package directory ships to end users.

## Canonical IDs

The directory name under `data/` **is** the `taskId`. It must be lowercase kebab-case, stable
forever, and identical to `taskPresetId` in `manifest.json`. Renaming a directory breaks
published detail and package URLs, so treat it as a new task instead.

| Display label | `taskId` |
| --- | --- |
| UI Master | `ui-master` |
| AgentsMD | `claude-md-update` |
| Last 30 Days | `last30days` |
| Ponytail | `ponytail` |
| Goal | `goal` |
| OpenSpec Spec Compress | `openspec-spec-compress` |

`agentsmd` and `portytail` are human-facing aliases only; they are not canonical IDs.

## Package Layout

```text
data/<taskId>/
  manifest.json                  # required — identity, version, owner, localization, entrypoints
  frontend/
    panel.json                   # required — task panel definition
    commands.json                # optional — only when the task ships a command catalog
  backend/
    task-preset.json             # required — task key, target type, requirements, scene binding
    prompts.json                 # required — prompt package (inputs, template engine, locales)
    templates/<locale>/
      system.md                  # required — system prompt template per locale
      user.hbs                   # required — user prompt template per locale
  locales/
    en-US.json                   # required — UI strings for the plugin namespace
    zh-CN.json                   # required
  store-page/
    index.en-US.md               # required — frontmatter drives catalog metadata
    index.zh-CN.md               # required
```

`en-US` and `zh-CN` are both required: the generated detail document declares
`locales/en-US.json`, `locales/zh-CN.json`, `store-page/index.en-US.md`, and
`store-page/index.zh-CN.md` as the package resources. Additional locales may be added
alongside them.

### What each file contributes to the published catalog

| File | Drives |
| --- | --- |
| `manifest.json` → `version` | `version` in index and detail |
| `manifest.json` → `owner` | `publisher` in index and detail |
| `manifest.json` → `localization` | which locale bundles the client loads |
| `backend/task-preset.json` → `requirements` | `requirements` plus the derived `compatibility` (agent / skills / cli) |
| `store-page/index.<locale>.md` → `title` | `name[<locale>]` |
| `store-page/index.<locale>.md` → `summary` | `summary[<locale>]` and `description[<locale>]` |
| `store-page/index.en-US.md` → `catalog` | `category` (first entry) and part of `tags` |
| `store-page/index.en-US.md` → `tags` | the rest of `tags` |

`category` falls back to the first `tags` entry, then to `General`, when `catalog` is
absent. Only the `en-US` store page contributes `catalog` and `tags`.

### `$schema` references and authoritative schemas

The validation baseline lives in the **nested `hagitask` submodule** at
`hagitask/schemas/task-preset-plugin/`. This repository no longer vendors its own copy of the
schemas; `hagitask` is the single authoritative schema source, consumed here through the
nested submodule and by `hagitask-site` through the same nested submodule. Every package
`$schema` reference points at the **public HagiTask Site URL**, so editors and CI can fetch it
directly without the submodule:

```text
https://tasks.hagicode.com/schemas/task-preset-plugin/<schema>.schema.json
```

`https://tasks.hagicode.com/schemas/` is the public distribution root. Its files are published
by the `hagitask-site` deploy workflow, which downloads the HagiTask repository at the commit
this repository's `hagitask` gitlink records and copies that checkout's `schemas/` tree into the
published payload — so the public URL and the nested submodule always serve the same revision.

The path tail (`schemas/task-preset-plugin/<name>.schema.json`) is preserved verbatim, so a
package still moves unchanged between `hagitask/presets/<taskId>/` and `data/<taskId>/`. The
local validator resolves each `$schema` reference by file name against the nested
`hagitask/schemas/task-preset-plugin/` directory (it matches on the `schemas/task-preset-plugin/`
segment of the URL), never reading outside that directory and never hitting the network, so the
public URL and the local submodule resolve to the same schema.

| Package file | `$schema` value |
| --- | --- |
| `manifest.json` | `https://tasks.hagicode.com/schemas/task-preset-plugin/manifest.schema.json` |
| `frontend/panel.json` | `https://tasks.hagicode.com/schemas/task-preset-plugin/panel.schema.json` |
| `frontend/commands.json` | `https://tasks.hagicode.com/schemas/task-preset-plugin/commands.schema.json` |
| `backend/task-preset.json` | `https://tasks.hagicode.com/schemas/task-preset-plugin/task-preset.schema.json` |
| `backend/prompts.json` | `https://tasks.hagicode.com/schemas/task-preset-plugin/prompt-package.schema.json` |
| `locales/<locale>.json` | `https://tasks.hagicode.com/schemas/task-preset-plugin/locales.schema.json` |

The two catalog schemas that describe the generated site output are published next to them at
`https://tasks.hagicode.com/schemas/community-index-v1.schema.json` (for `/index.json`) and
`https://tasks.hagicode.com/schemas/community-task-detail-v1.schema.json` (for
`/tasks/<taskId>.json`). Those documents are generated by `hagitask-site`, not authored here.

The upstream source of truth for every one of these schemas is
[`hagitask/schemas/`](https://github.com/HagiCode-org/hagitask/tree/main/schemas).
Initialize the nested submodule (see below) before validating so the schema root is present
for the local validator.

### Versioning

Bump `version` in `manifest.json` using semantic versioning on every published change.
The generated index, detail document, and package digest all follow from it, so an
unchanged version with changed content makes published metadata ambiguous.

## Contribute a Task

1. **Initialize nested submodules** so the schema source is available:
   `git submodule update --init --recursive`.
2. **Pick a canonical Task ID.** Lowercase kebab-case, unique across `data/`.
3. **Create `data/<taskId>/`** using the layout above. Copying the closest existing package
   (for example `data/ui-master/`) is the fastest start.
4. **Update `manifest.json`**: set `taskPresetId` to `<taskId>`, reset `version` to
   `1.0.0`, set `owner`, and point `localization.bundles`, `ui.*`, and `backend.*` at the
   files you actually ship.
5. **Keep every `$schema`** at the absolute `https://tasks.hagicode.com/schemas/` URL listed above.
6. **Write the locale bundles.** `locales/<locale>.json` holds the UI strings resolved
   through the manifest's `localization.namespace`. Keep the same key set in every locale
   so no language falls back silently.
7. **Write the store pages.** `store-page/index.en-US.md` and `index.zh-CN.md` need
   `locale`, `slug`, `title`, and `summary` in frontmatter; put `catalog` and `tags` in the
   `en-US` page because that is what the published `category` and `tags` are derived from.
   The Markdown body below the frontmatter is the long-form store description.
8. **Add the prompt templates** for every locale listed in `backend/prompts.json`.
9. **Validate locally** (see below).
10. **Open a Pull Request against this repository.** This repository — not `hagitask-site`
    — is the submission destination. After review and merge, `hagitask-site` bumps its
    `community-packages/` submodule pointer and the next site build publishes your
    `/index.json` entry, `/tasks/<taskId>.json`, and `/packages/<taskId>.zip`.

## Validate Locally

The fastest check runs entirely in this repository. It validates every package under `data/`
against the `hagitask/schemas/task-preset-plugin/` baseline, enforces canonical IDs and
uniqueness, and checks that declared resources, locale coverage, prompt templates, and
store-page frontmatter are complete and internally consistent.

```bash
git submodule update --init --recursive   # fetch the nested hagitask schema source
npm install
npm run validate        # exits non-zero with package/file/field errors on failure
```

`npm run validate` invokes `scripts/validate-community-packages.mjs`. The same command is
run by the `Validate Community Packages` workflow on every pull request that changes
package content and on every push to `main`. The `validate-packages` job from that workflow
is a **required status check**: a pull request that fails validation is blocked from
merging until the errors are fixed. Configure it as required under the repository's branch
protection for `main`.

You can also run the fixture tests for the validator:

```bash
npm test
```

The end-to-end site build remains the second line of defense. It runs the same
normalization and schema validation that publication uses, so a successful
`npm run build` means your package normalized cleanly:

```bash
git clone https://github.com/HagiCode-org/hagitask-site.git
cd hagitask-site
git submodule update --init --recursive   # fetches community-packages and its nested hagitask
npm install
npm run typecheck
npm run build                          # fails on malformed or missing package files
npm run stage:schemas                  # copies the schema tree into dist/schemas/
npm run verify                         # checks the index, details, archives, and schemas
```

A successful `npm run build` means the generated `/index.json` and `/tasks/<taskId>.json`
conform to the v1 community schemas.

When validation does fail, fix the source file in `data/<taskId>/`. Never work around it by
editing generated output — `/index.json`, `/tasks/<taskId>.json`, and
`/packages/<taskId>.zip` are rebuilt from scratch on every publish and hand edits are lost.

## Rules

- This repository is the only source of truth for these task definitions.
- Do not duplicate these definitions inside `hagitask-site`.
- Do not commit generated catalog output, package archives, or build artifacts here.
- Do not edit anything under `hagitask/`; schema changes belong in the `hagitask`
  repository and reach this one by advancing the nested submodule pointer.
- Bump `version` in `manifest.json` using semantic versioning when publishing a change.
