# hagitask-community-packages

Source of truth for the public HagiTask community catalog.

This repository is mounted by [`hagitask-site`](https://github.com/HagiCode-org/hagitask-site)
as its `data/` Git submodule. The site build reads these directories, validates them
against the v1 community schemas, generates `/index.json`, `/tasks/<taskId>.json`, and
downloadable `/packages/<taskId>.zip` archives, then publishes them as static assets.

## Source Data vs Generated Output

Every `<taskId>/` directory in this repository is **source data**. Everything the public
site serves is **generated** and must never be edited or committed by hand.

| Artifact | Where it lives | Who owns it |
| --- | --- | --- |
| `<taskId>/` package directories | this repository | contributors (edit here) |
| `data/` submodule | `hagitask-site` | pins a commit of this repository |
| `/index.json` | `tasks.hagicode.com` | generated by the site build |
| `/tasks/<taskId>.json` | `tasks.hagicode.com` | generated by the site build |
| `/packages/<taskId>.zip` | `tasks.hagicode.com` | generated by the site build |
| `schemas/task-preset-plugin/**` | this repository (vendored from [`hagitask`](https://github.com/HagiCode-org/hagitask)) | schema maintainers |

```text
hagitask-community-packages/<taskId>/      (you edit this)
        │
        │ git submodule → hagitask-site/data/
        ▼
hagitask-site build                        (normalize → validate → publish)
        │
        ├─ /index.json                     discovery index
        ├─ /tasks/<taskId>.json            detail document
        └─ /packages/<taskId>.zip          installable archive
```

The archive is a byte-stable zip of the whole `<taskId>/` directory, so any file you add
to the package directory ships to end users.

## Canonical IDs

The directory name **is** the `taskId`. It must be lowercase kebab-case, stable forever,
and identical to `taskPresetId` in `manifest.json`. Renaming a directory breaks published
detail and package URLs, so treat it as a new task instead.

| Display label | `taskId` |
| --- | --- |
| UI Master | `ui-master` |
| AgentsMD | `claude-md-update` |
| Last 30 Days | `last30days` |
| Ponytail | `ponytail` |
| Goal | `goal` |
| OpenSpec Spec Compress | `openspec-spec-compress` |

`agentsmd` and `portytail` are human-facing aliases only; they are not canonical IDs.

## Package Layout

```text
<taskId>/
  manifest.json                  # required — identity, version, owner, localization, entrypoints
  frontend/
    panel.json                   # required — task panel definition
    commands.json                # optional — only when the task ships a command catalog
  backend/
    task-preset.json             # required — task key, target type, requirements, scene binding
    prompts.json                 # required — prompt package (inputs, template engine, locales)
    templates/<locale>/
      system.md                  # required — system prompt template per locale
      user.hbs                   # required — user prompt template per locale
  locales/
    en-US.json                   # required — UI strings for the plugin namespace
    zh-CN.json                   # required
  store-page/
    index.en-US.md               # required — frontmatter drives catalog metadata
    index.zh-CN.md               # required
```

`en-US` and `zh-CN` are both required: the generated detail document declares
`locales/en-US.json`, `locales/zh-CN.json`, `store-page/index.en-US.md`, and
`store-page/index.zh-CN.md` as the package resources. Additional locales may be added
alongside them.

### What each file contributes to the published catalog

| File | Drives |
| --- | --- |
| `manifest.json` → `version` | `version` in index and detail |
| `manifest.json` → `owner` | `publisher` in index and detail |
| `manifest.json` → `localization` | which locale bundles the client loads |
| `backend/task-preset.json` → `requirements` | `requirements` plus the derived `compatibility` (agent / skills / cli) |
| `store-page/index.<locale>.md` → `title` | `name[<locale>]` |
| `store-page/index.<locale>.md` → `summary` | `summary[<locale>]` and `description[<locale>]` |
| `store-page/index.en-US.md` → `catalog` | `category` (first entry) and part of `tags` |
| `store-page/index.en-US.md` → `tags` | the rest of `tags` |

`category` falls back to the first `tags` entry, then to `General`, when `catalog` is
absent. Only the `en-US` store page contributes `catalog` and `tags`.

### `$schema` references

Keep the same relative `$schema` paths the shipped presets use, so a package can move
between `hagitask/presets/<taskId>/` and this repository unchanged:

| Package file | `$schema` value |
| --- | --- |
| `manifest.json` | `../../schemas/task-preset-plugin/manifest.schema.json` |
| `frontend/panel.json` | `../../../schemas/task-preset-plugin/panel.schema.json` |
| `frontend/commands.json` | `../../../schemas/task-preset-plugin/commands.schema.json` |
| `backend/task-preset.json` | `../../../schemas/task-preset-plugin/task-preset.schema.json` |
| `backend/prompts.json` | `../../../schemas/task-preset-plugin/prompt-package.schema.json` |
| `locales/<locale>.json` | `../../../schemas/task-preset-plugin/locales.schema.json` |

The schema files are **vendored in this repository** at
`schemas/task-preset-plugin/` so validation can run offline after a plain clone, and they
are the validation baseline that every package is checked against. The upstream source of
truth for these schemas is
[`hagitask/schemas/task-preset-plugin/`](https://github.com/HagiCode-org/hagitask/tree/main/schemas/task-preset-plugin).
Keep the `$schema` paths above unchanged so a package can move between `hagitask/presets/<taskId>/`
and this repository; the validator resolves each `$schema` reference against this
repository's `schemas/task-preset-plugin/` directory by file name (never reading outside
the repository).

### Versioning

Bump `version` in `manifest.json` using semantic versioning on every published change.
The generated index, detail document, and package digest all follow from it, so an
unchanged version with changed content makes published metadata ambiguous.

## Contribute a Task

1. **Pick a canonical Task ID.** Lowercase kebab-case, unique across this repository.
2. **Create `<taskId>/`** using the layout above. Copying the closest existing package
   (for example `ui-master/`) is the fastest start.
3. **Update `manifest.json`**: set `taskPresetId` to `<taskId>`, reset `version` to
   `1.0.0`, set `owner`, and point `localization.bundles`, `ui.*`, and `backend.*` at the
   files you actually ship.
4. **Set every `$schema`** to the relative path listed above.
5. **Write the locale bundles.** `locales/<locale>.json` holds the UI strings resolved
   through the manifest's `localization.namespace`. Keep the same key set in every locale
   so no language falls back silently.
6. **Write the store pages.** `store-page/index.en-US.md` and `index.zh-CN.md` need
   `locale`, `slug`, `title`, and `summary` in frontmatter; put `catalog` and `tags` in the
   `en-US` page because that is what the published `category` and `tags` are derived from.
   The Markdown body below the frontmatter is the long-form store description.
7. **Add the prompt templates** for every locale listed in `backend/prompts.json`.
8. **Validate locally** (see below).
9. **Open a Pull Request against this repository.** This repository — not `hagitask-site`
   — is the submission destination. After review and merge, `hagitask-site` bumps its
   `data/` submodule pointer and the next site build publishes your `/index.json` entry,
   `/tasks/<taskId>.json`, and `/packages/<taskId>.zip`.

## Validate Locally

The fastest check runs entirely in this repository. It validates every package against the
vendored `schemas/task-preset-plugin/` baseline, enforces canonical IDs and uniqueness,
and checks that declared resources, locale coverage, prompt templates, and store-page
frontmatter are complete and internally consistent:

```bash
npm install
npm run validate        # exits non-zero with package/file/field errors on failure
```

`npm run validate` invokes `scripts/validate-community-packages.mjs`. The same command is
run by the `Validate Community Packages` workflow on every pull request that changes
package content and on every push to `main`. The `validate-packages` job from that workflow
is a **required status check**: a pull request that fails validation is blocked from
merging until the errors are fixed. Configure it as required under the repository's branch
protection for `main`.

You can also run the fixture tests for the validator:

```bash
npm test
```

The end-to-end site build remains the second line of defense. It runs the same
normalization and schema validation that publication uses, so a successful
`npm run build` means your package normalized cleanly:

```bash
git clone https://github.com/HagiCode-org/hagitask-site.git
cd hagitask-site
git submodule update --init            # or point data/ at your working copy
npm install
npm run typecheck
npm run build                          # fails on malformed or missing package files
npm run verify                         # checks the published index, details, and archives
```

A successful `npm run build` means the generated `/index.json` and `/tasks/<taskId>.json`
conform to the v1 community schemas.

When validation does fail, fix the source file in `<taskId>/`. Never work around it by
editing generated output — `/index.json`, `/tasks/<taskId>.json`, and
`/packages/<taskId>.zip` are rebuilt from scratch on every publish and hand edits are lost.

## Rules

- This repository is the only source of truth for these task definitions.
- Do not duplicate these definitions inside `hagitask-site`.
- Do not commit generated catalog output, package archives, or build artifacts here.
- Bump `version` in `manifest.json` using semantic versioning when publishing a change.
